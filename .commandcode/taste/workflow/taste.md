# Workflow

- Prefers subagent-driven development: delegate codebase exploration and research to parallel subagents before implementing. Confidence: 0.9
- Uses /yolo to let the agent continue autonomously without pausing for confirmation at each step. Confidence: 0.7
- Creates fix branches from `main` using `fix/issue-<number>` naming when working on an issue fix. Confidence: 0.6
- Expects commits to follow the repository's established commit conventions (Conventional Commits style matching the existing git log when no formal spec/commitlint exists) rather than an ad-hoc format. Confidence: 0.7
- Wants every commit to include a `-s` (DCO sign-off) trailer line, and asks for it explicitly when handing over a commit-and-push task ("按repo规范提交并推送，额外带-s"). Confidence: 0.75
- Splits a feature into multiple logically-scoped commits by concern (e.g. backend engine versus frontend/UI) rather than one monolithic commit, each with its own conventional-commit message. Confidence: 0.6
- When opening PRs to an upstream repository, expects them to follow the repo's contributing guide and industry conventions (checks CONTRIBUTING.md, PR templates, changelog/CI workflows, and the upstream's existing PR title style) rather than ad-hoc formatting. Confidence: 0.8
- Before opening a PR, runs the verification commands the contributing guide specifies (e.g. feature-flagged `cargo check`) so claims in the PR description are accurate. Confidence: 0.55
- Expects PR descriptions to be structured and to end with a `Closes #<issue>` trailer so merging auto-closes the linked issue. Confidence: 0.6
- When a review comment lands on an open PR (shared as a link, even bot reviews like Sourcery or axl-bot), expects the agent to handle it end-to-end without further instruction: fetch the review, fix the code, add regression tests covering the new behavior, run targeted verification (fmt + relevant tests), commit and push, then reply on the PR explaining the resolution with commit hash and test results. Confidence: 0.7
- Keeps PR branches in sync with the upstream baseline, and does so in bulk: asks to update "all the PRs listed upstream", expecting the agent to fetch upstream, report each branch's behind/ahead count, then bring every open PR branch up to upstream main in one run. Explicitly and non-negotiably prefers merge over rebase for syncing upstream into a PR branch ("同步上游更新到 PR 分支时优先用 merge，不要用 rebase") — rebasing rewrites the PR's commits and can dismiss an existing approval, so preserving an already-APPROVED review outranks linear history; pushing new commits for a merge is the accepted cost, and merge conflicts surfaced by the sync are treated as part of that same job — the user flags them upfront when handing the task over (注意更新分支以及处理可能的冲突) and expects them resolved in the run. Confidence: 0.85
- After syncing branches, expects the result to be verified and reported per PR: re-confirm compilation on the branch with the riskiest changes, check each PR is left MERGEABLE with zero commits behind, and end the run back on the previously checked-out branch with a clean working tree. Confidence: 0.6
- Engages an explicit planning phase before implementing non-trivial fixes or follow-ups: invokes /plan (or asks for a written 计划方案) and expects the plan to absorb all accumulated suggestions — bot-review blockers and optional/non-blocking review feedback alike — before any code is changed. Confidence: 0.6
- After an upstream PR is merged, expects a full post-merge cleanup run autonomously: confirm merge status and issue auto-closure (via gh), prune/delete the feature branch locally and on the fork remote (using `-D` if a squash merge defeats `-d`), return to main and fast-forward it to upstream, keep the fork's main in sync with upstream, then report the closed-out state. Confidence: 0.7
- Wants frontend/feature work to start with a read-only exploration phase that gathers repo context (layout/scroll containers, keyboard/keyboard-shortcut infrastructure, reusable components, i18n conventions) via parallel explore subagents before proposing an implementation direction. Confidence: 0.8
- Prefers a single global implementation over per-page duplication when the targets share one underlying infrastructure element (e.g. several pages mounting into the same scroll container `.app-viewport`) — one root-level change covers all targets. Confidence: 0.8
- Once the general implementation supersedes a local duplicate, expects the duplicate to be deleted outright rather than left in place (had the browse tab's own scroll-to-top button removed, with the global one taking over, instead of keeping both behind a route guard). Confidence: 0.85
- For frontend changes, expects the project's own check chain to pass before committing and to be reported honestly: type check, lint, i18n consistency check, unit tests — with pre-existing failures isolated (e.g. verified on a stashed baseline) rather than silently claimed as green. Confidence: 0.7
- Wants new user-facing strings routed through the project's i18n pipeline with both locale catalogs updated (en-US and zh-CN) and message ids kept in sync with the ids used in components, so the repo's i18n consistency check stays green. Confidence: 0.7
- Prefers reusing and retrofitting an existing component/config (e.g. globalizing an `ScrollToTopButton` and moving its hard-coded tooltip through the i18n pipeline) over building a fresh parallel one. Confidence: 0.75
- Before concluding "existing tests fail because of my change", isolates them with `git stash` and re-runs on the baseline to confirm they were already broken upstream; only genuinely novel failures count against the change. Confidence: 0.7
- New user-facing settings/features (e.g. keyboard shortcuts) should default to OFF and be opt-in individually via the settings page, rather than enabled by default. Confidence: 0.85
- Prefers to "sediment" (沉淀) proven, repeatedly-executed workflows into reusable skills — signaling this with a `skills:` prefix — so the process can be re-invoked later instead of re-explained; expects the skill to be built through the skill-creator flow and placed following the repo's existing skill conventions. Confidence: 0.7
- For PR review, prefers a multi-perspective review by several independent parallel subagents, each reviewing from a distinct angle (e.g. correctness/logic, style & tests, security & external validation), and treats the cross-validated findings as authoritative blockers to fix. Requested as "多视角子代理 /review" (same as last time), indicating an established repeatable flow. Confidence: 0.8
- Surfaces genuine design forks (key mappings, default semantics, feature scope) to the user as an interactive question with the recommended option listed first and the trade-off explained in each option, rather than deciding unilaterally — answered quickly and prevents rework. Confidence: 0.75
- Expects plan documents written as markdown plan files (under `~/.commandcode/plans/`) containing file:line evidence, confirmed design decisions, a per-file change list, the verification commands and an execution order — not just an in-chat outline. Confidence: 0.7
- Keeps infrastructure/CI changes in a dedicated PR (own branch, e.g. `fix/ci-…`) rather than mixing them into a feature PR, so reviewers can evaluate and revert them independently. Confidence: 0.7
- Prefers completeness over caution when the same defect recurs elsewhere: when a fix has an identical counterpart in another file/workflow, expects it to be fixed in the same change rather than left behind because it cannot be validated by the current PR's CI (explicitly asked to include the release workflow in the CI caching fix). Confidence: 0.6
- When a failing check or a regression is reported on a PR, expects root-cause attribution backed by evidence: decide explicitly whether it was introduced by the change, already existed on the baseline, or is repository infrastructure (e.g. fork-PR token restrictions on the changelog bot) — locating the offending commit with `git blame`/`git log -S`, reproducing the check locally with the repo's own tooling, and corroborating against other fork PRs' runs — then report both the evidence and the verdict on the PR rather than assuming blame or chasing an unfixable check. Confidence: 0.75
- For an action carrying several parameters (e.g. exporting logs), expects the granularity/options to be presented in a modal dialog first and the action performed from it, rather than executing with implicit defaults. Confidence: 0.6
- Expects to be able to verify a change by actually running a build: asks whether CI publishes downloadable build artifacts, and when none exist requests local builds of the specific PR branches, handed over as installer + raw binary with sizes, SHA-256 checksums, build logs and concrete manual-verification steps. Confidence: 0.7
- After producing builds, expects build side effects on tracked files (e.g. a build step regenerating `contributors.json`) to be reverted and the working tree left clean back on the previously checked-out branch, so branches are not polluted by the build. Confidence: 0.6
- Treats slow/blocked CI as a defect worth fixing at the root: expects the diagnosis to be backed by job logs and per-step conclusions (e.g. identifying a step that silently never ran) and the broken mechanism replaced robustly rather than patched around its symptom. Confidence: 0.6
- Expects new UI/settings surfaces to match the repository's existing implementations instead of inventing their own variant: reported the shortcut-settings rows as "排版异常，与其他实现未对齐", and the fix dropped the stacked layout and a locally-invented label component in favour of the standard two-column settings row plus a proper section heading. Confidence: 0.7
- Keyboard-first: expects keyboard navigation to work end-to-end, not just mouse flows — after a page is chosen from the menu, focus must land in the page content so Tab continues into the page instead of walking the nav rail, and the off/on state of each shortcut must be authoritative. Confidence: 0.6
- Expects new branches/PRs to be opened only when explicitly asked: when implementation is deferred, wants the round to end with nothing created (and the clean state verified via git), the work captured instead as a persisted draft to resume from in a later round. Confidence: 0.6
- For a defect judged to be the upstream project's design fault (e.g. local/test builds sharing the installed app's identifier, so they clobber the real data directory and database), wants it framed as an upstream issue first and a draft PR after, rather than patched around locally; a manual per-run workaround does not count as the fix. Confidence: 0.55
- Treats the user's real app data/database as untouchable by default: never modified without asking first, and any destructive repair is rehearsed on a disposable copy, backed up with a timestamp, then verified afterwards (integrity check plus per-column comparison against the pre-change values). Confidence: 0.6
- Expects fatal error / initialization-failure states to stay escapable: a full-screen error overlay that covers the whole GUI (including tray and window controls), offers no close control, and leaves force-killing the process as the only way out is a defect, not just an inconvenience — failure paths must keep a reachable way to quit. Confidence: 0.6
- Wants a destructive manual recovery procedure (e.g. rolling a database back past an applied migration) productized as a checked-in, rerunnable script instead of ad-hoc commands or hand-holding — and expects that script to be safe by default (dry run unless explicitly told to apply, timestamped backup taken first, refusal with a clear reason rather than a guess when it cannot act safely). Confidence: 0.65
- Wants a new reusable UI capability delivered as a shared component in the common UI package (`packages/ui`), with a clean props/emit API and no knowledge of the consuming feature, rather than inlined into the one feature that needs it today — explicitly asked for a "Modal 公共组件" that the shortcut feature then consumes. Confidence: 0.7
- Expects the agent to load/activate the user's own skill library under `~/.agents/skills` when asked (e.g. `ui-ux-pro-max` for accessibility/UX rules, `vibehub` for converging fuzzy requirements) and to let those skills actually steer the design. Confidence: 0.7
- On "沉淀会话 / 压缩上下文历史" or "更新会话，创建交接文档，我将在新会话继续", expects the session to be distilled into persisted artifacts a later session can resume from: the reusable skill updated with the new lessons **and** the handoff snapshot kept at the canonical path `~/.commandcode/plans/session-handoff.md` (updated in place rather than recreated) covering in-flight PR/branch state, root-cause conclusions, environment/data state, verification results and pending todos — written to stand in for the conversation history in the next session. Expects earlier assumptions that turned out wrong to be called out explicitly rather than silently corrected. Confidence: 0.8
- Expects a red CI after a merge-based baseline sync to be attributed to its real source, including the case where the merge result inherited upstream's own transient breakage (a field added in one upstream commit and initialised only in the next, so any PR merging inside that window fails to compile on every platform): the remedy is to sync upstream again rather than patch code the change never touched, verified locally with the exact command CI runs. Confidence: 0.6
